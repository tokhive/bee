# Bee 账户页前端交互规格：mock 阶段

日期：2026-11-05。按 `mattpocock-skills:to-spec` 综合讨论整理。

状态：用户已批准并授权实施；前端与有状态 mock 阶段已完成。目标行为仅在开发预览的 `accounts-auto-*` 场景启用，不接真实业务，不改变当前原生后台运行规则。5 项任务作为本地执行记录维护，未发布外部 issue。结果见[验收记录](evidence/2026-11-04-account-ui-review/auto-service-validation.md)。

## Problem Statement

用户需要先确认 Bee 账户页是否清楚、简洁，接入、暂停恢复、重新登录、换号及故障处理能否连续完成。目前“开始贡献”与“恢复接单”容易混淆，状态和错误说明存在重复；只切换静态截图也无法判断实际操作顺序是否顺畅。

此时接入真实账号、Hive 和本机运行模块会扩大范围。当前要回答的是：用户能否通过界面正确完成流程，前端状态、按钮、反馈和恢复路径是否一致。

## Solution

先通过独立 HTML 预览讨论目标交互，再在现有正式前端与 mock 预览入口跑通账户页。页面、前端状态协调、按钮逻辑和反馈实际运行；账号、额度、授权、服务运行、Hive 响应、登录结果、断线与重启都由有状态 mock 提供。

目标交互保持已讨论的方向：移除日常“开始贡献／停止贡献”按钮，展示服务自动准备；用户明确接入账号，并分别暂停／恢复接单。接入、确认换号和主动重新登录后保持暂停，正常重连与同身份后台刷新保留暂停选择。

每个账号只有一条主状态，原因默认折叠，同因去重、独立条件保留。通过连续操作和可控失败来验证界面，而非直接跳到预设成功画面。本阶段通过表示前端流程在 mock 条件下成立，不代表真实接单、授权维护或原生后台运行已实现。

## User Stories

1. 作为账户页用户，我希望只管理平台接单选择，以便不再寻找另一个“开始贡献”按钮。
2. 作为未接入账号的用户，我希望清楚看到登录或接入入口，以便知道下一步操作。
3. 作为尚未完成配对的用户，我希望得到准确的配对引导，以便不会误以为可以直接接入并接单。
4. 作为已有官方登录的用户，我希望先查看候选账号再确认接入，以便避免选错订阅。
5. 作为接入账号的用户，我希望确认框说明目标账号、额度使用和暂停范围，以便理解操作影响。
6. 作为刚接入账号的用户，我希望在账户页直接继续操作，以便无需转到概览启动贡献。
7. 作为刚接入账号的用户，我希望平台保持暂停，以便自行决定何时恢复接单。
8. 作为使用两个平台的用户，我希望分别暂停和恢复平台，以便控制每个平台的状态。
9. 作为恢复接单的用户，我希望看到进行中、成功或失败的反馈，以便知道操作是否完成。
10. 作为存在其他阻碍的用户，我希望恢复接单后仍能看到未解决的问题，以便不会把解除暂停误认为全部正常。
11. 作为权限不足的用户，我希望展开具体原因并进入读取设置，以便找到与问题对应的处理入口。
12. 作为同时遇到权限错误和暂停的用户，我希望看到两个独立原因，以便不会遗漏接单条件。
13. 作为完成权限修复的用户，我希望平台仍保持暂停，以便修复不会替我开启接单。
14. 作为查看状态的用户，我希望每个账号只突出一条主状态，以便快速理解当前情况。
15. 作为查看错误的用户，我希望重复原因合并且详情默认折叠，以便页面保持简洁。
16. 作为需要重新登录的用户，我希望从目标平台直接开始，以便无需先手动停止全局贡献。
17. 作为主动登录的用户，我希望知道该平台将暂停及可能的任务影响，以便决定何时继续。
18. 作为重新登录原账号的用户，我希望登录完成后仍保持暂停，以便明确选择恢复接单。
19. 作为取消或登录失败的用户，我希望得到真实可用的下一步，以便继续核对或重试而不必重新开始全部流程。
20. 作为检测到不同账号的用户，我希望看到当前与目标账号的对比并确认换号，以便不发生自动切换。
21. 作为确认换号的用户，我希望新账号仍保持暂停，以便检查后再恢复接单。
22. 作为使用两个平台的用户，我希望一个平台的错误或登录进度不覆盖另一个平台，以便分别理解其状态。
23. 作为修改读取来源的用户，我希望输入被保留且旧结果不会覆盖新来源，以便正确完成修复。
24. 作为遇到响应丢失的用户，我希望看到结果待确认并能核对原结果，以便不会重复提交操作。
25. 作为遇到过期报告的用户，我希望界面显示状态待更新，以便不会把旧结果当成当前可用状态。
26. 作为经历断线恢复的用户，我希望原来的暂停选择保持，以便重连不会改变我的意图。
27. 作为在列表和详情之间切换的用户，我希望两处反映同一份状态，以便不会看到互相矛盾的信息。
28. 作为键盘或窄窗口用户，我希望主要动作、原因和详情均可访问，以便完整完成流程。
29. 作为英文或深色界面用户，我希望状态与按钮清楚且不溢出，以便外观和语言不会妨碍操作。
30. 作为评审者，我希望能控制成功、失败、取消、超时、断线和模拟重启，并从起点连续操作，以便确认前端逻辑覆盖关键路径。

## Implementation Decisions

1. **范围限定为前端。** 本阶段仅落实页面、呈现逻辑、前端状态协调及其 mock 交互。真实 Hive、Go 账号与运行逻辑、Rust／Tauri 生命周期、官方客户端和凭据存储不接入、不修改。
2. **先讨论，再落到真实前端。** 独立 HTML 用于快速确认交互；前端逻辑验收使用现有正式页面、共享状态及类型化 Client，接入既有模拟 IPC。HTML 点击通过不能替代正式前端流程验收。
3. **复用现有预览模式。** 新行为先在明确的 mock 环境验证，不把原生后端尚未支持的自动运行描述为已经接通。模拟控制与产品页面分开呈现，不把开发细节放入正常用户流程。
4. **使用有状态 mock。** 接入、暂停、恢复、登录和换号通过正常页面动作更新模拟状态；同一会话中列表、详情和必要的概览信息保持一致。切换场景或显式重置才重新初始化。
5. **不复制一套后端。** mock 只表达前端所需的状态、操作结果和时序，不实现真实授权、调度、结算或进程管理。优先沿用现有接口与场景；缺少的模拟能力记录为依赖，不能靠直接改 DOM 或切换截图冒充流程成功。
6. **模拟自动运行的目标体验。** 取消 mock 目标流程中的日常贡献启停按钮。无账号显示等待接入；接入后模拟服务准备和授权同步，平台仍暂停；准备失败时有具体状态及可继续操作的入口。
7. **平台控制独立。** 暂停／恢复只更新目标平台；前端根据当前模拟事实判断可接单、不能接单或状态待更新，不用操作成功提示替代当前结论。
8. **正常恢复保留选择。** 模拟断线、重连、同身份凭据刷新及服务重新打开时，保留各平台原来的暂停选择。模拟重启在当前测试会话中保留必要状态，不据此宣称真实持久化通过。
9. **主动登录后保持暂停。** 模拟目标平台暂停、登录进行中、成功、失败、取消和结果核对。原账号登录成功后仍暂停；不同身份等待明确换号；不能确认时显示问题。另一平台状态不受覆盖。
10. **接入和换号必须明确确认。** 候选登录不等于已接入；确认框保留目标身份、额度用途与暂停范围。来源或候选发生关键变化时，旧确认不能提交。
11. **未决操作不冒充成功。** 重复点击、迟到结果、切页、取消及响应丢失都通过同一前端状态链处理。结果未知时核对原操作，不自动重复提交接入、换号或恢复。
12. **单一状态与原因折叠。** 每个账号一条主状态；同因去重，独立原因展开可见。只有暂停时不再叠加“已暂停”等重复描述；权限错误与暂停分别解除。
13. **保留恢复与焦点行为。** 原因中提供“打开读取设置”等对应入口；读取方式在详情默认展开，定位时聚焦字段并保留输入。详情和确认框支持 Escape、焦点约束与返回。
14. **沿用视觉与技术。** 使用当前字体、颜色、间距、组件及 React／TypeScript 技术栈，无新增依赖。账户页优先，概览只作删除贡献启停交接所需的最小模拟调整。

## Testing Decisions

**本阶段测试边界：真实前端＋有状态 mock。** 用户提出先不接真实业务，因此不再以前述真实账号与运行模块作为当前主要测试入口。

1. **主要入口是浏览器中的真实页面。** 通过点击、键盘、表单和弹窗驱动正式前端，后台由现有模拟 IPC 返回数据。观察用户可见状态、可用操作和前端发出的命令，不测试内部变量或 DOM 实现细节。
2. **连续验证正常流程。** 候选登录 → 明确接入 → 自动准备的模拟反馈 → 保持暂停 → 恢复接单 → 可接单 → 暂停接单。全过程保持同一会话，不用场景跳转代替中间步骤。
3. **连续验证登录与换号。** 原账号重新登录后保持暂停；登录为新身份后必须确认换号，换号后仍暂停；失败和取消能继续核对；操作一个平台时另一平台显示稳定。
4. **连续验证故障恢复。** 权限错误＋暂停 → 展开两项原因 → 修改模拟来源条件 → 重新核对 → 权限恢复但暂停保留 → 明确恢复。检查过期报告、断线、响应丢失、重复点击、旧结果晚到及模拟重启。
5. **验证共享状态与操作反馈。** 列表与详情一致，历史成功提示不与当前状态冲突；进行中防重复提交，失败有下一步，结果待确认不会直接显示成功。
6. **复用已有测试设施。** 使用现有账户页、运行预览、有状态场景及 Playwright 先例。只补与本次前端变化相关的行为检查；不新建 Go／Rust 集成测试，也不为独立讨论 HTML 编写镜像实现的测试。
7. **验证可访问性与布局。** 覆盖 860×600 窄窗、中英文、明暗主题、键盘、原因展开、Escape 和焦点返回；每账号一条主状态，主要动作可见，没有横向溢出。
8. **区分能力缺口。** 页面逻辑错误与 mock 缺少结果控制分别记录。未能模拟或未实际走通的路径不得标记通过；静态场景展示仅证明该状态可呈现。
9. **限定验收结论。** 只报告“前端流程在 mock 下通过”。真实任务是否派发、授权是否安全更新、退出是否回收进程及磁盘状态是否恢复，由后续业务联调验证。

## Out of Scope

- 真实 Hive、真实账号、真实官方登录、凭据读取与实际模型请求。
- Go／Rust／Tauri 后台行为修改、真实自动运行、原生关窗退出、更新与网络重启。
- 后端任务处理、授权发布时序、真实重启持久化、旧版本数据迁移及真实任务中断验证。
- 其他页面的完整视觉重做、配对流程重做、多账号池、已注册账号完整移除、收益与资金页面。
- 新的后端协议、系统守护服务、部署架构或独立业务模拟框架。
- 自动接入候选账号、自动确认换号、因修复问题而自动解除暂停。
- 将本阶段目标行为直接启用于真实原生运行或发布产品。
