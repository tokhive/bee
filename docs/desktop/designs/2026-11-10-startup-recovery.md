# Bee 启动阻塞与自动恢复方案

状态：用户于 2026-11-11 授权实施；代码、主预览和开发包已落地。受控验证通过；真实旧脏会话的接管依赖与原生窗口验收缺口见[验收记录](../evidence/2026-11-11-startup-recovery/README.md)。
创建：2026-11-10；修订：2026-11-11（Asia/Shanghai）。
场景：[PENDING-001](../pending-scenarios.md)。
工作区：`bee-desktop-ui`；仅修改此 worktree。本文为已授权处理规格，实施任务见[计划](2026-11-11-startup-recovery-plan.md)。

## 1. 目标与已确认事实

让用户在启动受阻时看到准确原因，有安全、可验证的恢复路径。保留账号、设备绑定及最新接单选择。

原生 App 的只读查询已确认：管理状态 `stopped`，启动状态 `blocked`，错误 `OWNED_EXIT_UNCONFIRMED`。原因链为：旧恢复保护记录不干净 → 自动恢复拒绝 → 停止流程无法为旧会话确认安全退出 → 本次管理子进程被回收。重启重复该链路。

前端有两个缺口：未 ready 且无 `native.error` 时统一显示“正在读取 Bee…”；管理状态切换到停止时可能清掉 `startup` 记录。没有明确错误显示和恢复入口。保护记录最初由哪次退出产生，仍未查明。

已确认的边界：不删除保护文件、不自动解除暂停、不重放结果未知的账号操作、不因进程被回收就认定远端工作已撤销。正常退出与异常停止的安全条件继续生效。

## 2. 推荐方案与取舍

推荐：自动恢复管理后台，自动核对旧任务、未决操作与设备归属；有充分安全证据且原运行意图仍有效时自动恢复原运行状态。自动处理不了时停止推进，展示具体阻塞原因和人工入口。此方向已由用户在侧边讨论确认。

| 方案 | 完整性 | 业务复杂度 | 实现复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| 仅替换加载文案 | 能解释失败，无法恢复 | 低 | 低 | 只能作为修复的一部分 |
| 自动清理旧记录再启动 | 缺少旧任务、归属与未决写证明 | 表面低，隐含自动接管规则 | 表面低，破坏保护边界 | 不采用 |
| 保留管理能力＋每次手动确认恢复 | 有恢复出口，但要求用户先操作 | 每次启动故障均需人工 | 扩展现有启动链路与原操作记录 | 旧候选，已由自动优先方向替代 |
| 自动核对并恢复原状态，失败后人工处理 | 覆盖自动优先、真实进度与安全阻塞 | 证据充分时自动推进，阻塞后按原因处理 | 扩展现有启动链路、结构化资格与持久记录 | 推荐 |
| 重建通用任务／恢复平台 | 可覆盖，但超出本问题 | 高 | 高 | 本轮不引入 |

沿用现有原生进程监管、设备锁、准备保护和状态查询。没有引入新平台的必要。

## 3. 用户界面与操作

沿用现有桌面样式，采用已确认的紧凑“主标题＋一行子状态”。导航始终可用，账号页保留用户当前位置；概览与账号页读取同一个启动状态，不各自启动恢复。阻塞时再展示一个与原因匹配的主要动作、单层错误详情及诊断入口。

### 自动优先的默认流程

```text
正在恢复 Bee…
正在确认上次任务是否结束…
```

启动协调器自动连接／创建本 App 管理的后台，先进入只读恢复模式，不要求先点击“重新连接”。只有旧子进程已被确认回收、退出流程已结束、独占锁可取得时才能创建；其他进程仍占用时明确提示，不强杀其他进程。

连接阶段不准备账号、注册供给、刷新凭证或恢复接单。连接成功后自动核对第 4.2 节准入；满足全部条件后才转入恢复原运行状态，不弹出常规恢复确认框。已暂停账号保持暂停；原来允许接单的账号在恢复后可能接收任务。原意图为停止时只恢复管理能力，原意图未知时阻塞，不能推定需要启动服务。

新版首次启动也先分类旧保护状态，避免重演“恢复拒绝→清理失败→结束管理进程”。每次启动最多自动发起一次管理重连及一次符合资格的业务恢复；失败后保留本次尝试结果，不由渲染、切页或轮询触发新尝试。App 重启先查原持久记录，不能通过重启刷新失败预算；已有失败或未决记录时先核对，确定失败后等待人工处理再重试。该尝试预算已随 2026-11-11“实施”指令确认。

### 一行真实子状态

下列文案仅在对应阶段实际执行时展示，不要求每次经过全部阶段：

| 真实阶段 | 子状态 |
| --- | --- |
| 连接管理后台 | 正在连接后台… |
| 核对旧任务与未决操作 | 正在确认上次任务是否结束… |
| 核验设备、绑定与账号范围 | 正在核对设备与账号状态… |
| 执行账号准备 | 正在准备账号（2/3）… |
| 回读恢复结果 | 正在确认服务是否恢复… |

阶段、操作 ID、阶段版本和可选计数由实际执行端产生，经原生协议透传。计数表示当前操作中已完成准备的账号数／计划准备总数；没有可信总数时只写“正在准备账号…”。失败不得算作准备完成，旧操作事件不能覆盖新操作。禁止定时切换文案、估算百分比或把等待包装成持续推进。

### 自动处理不了时

停止自动推进后，主标题改为具体结果，子状态解释已确认的阻塞原因。例如确实查到旧任务结果未知时：

```text
暂时无法恢复 Bee                           [核对结果]
上次任务的结果尚未确认，暂未重新启动服务。
▸ 错误详情                                  查看诊断
```

- 管理连接已确定失败：显示实际连接失败原因，提供“重新连接”；其作用仅为重新进入连接与核对流程，不能跳过准入。
- 原操作仍未决或查询超时：“核对结果”只查询原操作，不新建或重放恢复。关闭页面不取消后台操作。
- 已确定失败且证明可重试：显示失败点与“重试恢复”；重新检查原意图和全部准入，原范围内恢复无需常规确认弹窗。
- 归属不明、记录损坏、签名或升级校验失败：显示具体阻塞项，提供已有的对应处理入口；没有安全自助能力时提供“查看诊断”与本地导出，不显示无效恢复按钮。
- 人工点击不能替代安全证明。若需要启动原本已停止的服务、改变账号范围或解除暂停，走对应的既有显式操作与确认流程，不属于自动恢复。
- 成功后回到正常布局，提示“服务已恢复，接单选择保持不变”；各账号独立展示凭证、额度、暂停等状态。仅管理恢复而原意图为停止时明确显示“后台已连接，服务未启动”。

恢复使用空的显式解暂停列表，以 Hive 最新可信选择为准；读取失败时阻塞，不能把未知当作“允许”。

### 等待与异常展示规则（已确认）

- 有明确 `blocked`、`failed`、`stopped` 结果时立即反映事实。只有协调器实际开始新的恢复阶段时才显示“正在恢复 Bee…”，原失败保留在详情；没有正在执行的恢复时不得继续显示加载。
- 普通启动使用“正在启动 Bee…”；故障恢复使用“正在恢复 Bee…”。子状态严格对应当前真实阶段，不仅凭管理进程 ready 推定服务已恢复。
- 同一阶段持续 10 秒：补充“等待时间较长，可查看诊断”，不宣告失败、不新增业务操作。
- 纯状态查询采用有截止的调用；失败后最多按 1／2／4 秒重试三次，同一查询不重叠，一轮自动核对最多 60 秒。仍在途的请求不得因计时结束被当作已终止。
- 自动核对停止后显示“状态待核对”及最后确认时间，提供手动核对；后台终态事件仍可更新页面。前端 60 秒核对期限不改变原生恢复现有的 90 秒等待／清理规则。
- 未确认启动期间，侧栏显示“连接状态待确认／服务状态待确认”；已有明确停止证据时才显示“服务已停止”。历史账号与额度标为上次记录。
- 自动阶段更新不抢焦点；人工操作结束后焦点回到触发按钮，原按钮消失时移到状态标题。状态更新可由辅助技术读取，无无限动画伪装失败。

## 4. 后台处理边界

### 4.1 管理与账号服务分离

管理进程负责读取、诊断和接受受控命令；账号服务负责准备与供给。业务启动受阻不等于管理进程必须退出。

新增恢复分类必须来自 Go 的结构化结果，不能由 Rust／前端匹配英文错误串。该分类与原始失败证据一起透传 Go → bridge → Rust → TypeScript；严格解码与能力声明同步更新。恢复能力返回可执行动作与具体阻塞理由，旧版本未声明能力时只展示诊断，不显示虚假的恢复入口。至少区分：

| 分类 | 必须证明的事实 | 行为 |
| --- | --- | --- |
| 启动前因继承旧会话被拒绝 | 拒绝发生在本次会话预留、工作线程及外部写入之前 | 留在管理只读模式，允许核对恢复资格 |
| 已启动后失败 | 已取得当前会话或发出外部动作 | 继续现有停止／清理流程，不能走前一例外 |
| 结果或归属未知 | 无法证明旧任务已经结束，或未决操作存在 | 禁止新启动，只核对原记录 |
| 数据、签名、升级或权限校验失败 | 对应检查明确拒绝 | 保留具体原因，不开放通用恢复绕过 |

现有 `reserveRuntimeSession` 可能在返回错误前写入保护记录，因此不能把所有 reservation error 都当作“没有发生动作”。需把该可恢复分类的检查放在副作用之前，并以测试证明。保留其他错误的清理规则。

### 4.2 自动与人工恢复共用的准入

Go 在设备独占锁和现有生命周期互斥下判定，Rust 串行协调管理进程、退出、更新与恢复。前端只消费结果。

提交前必须同时满足：

1. 本次签名与协议验证通过，当前管理实例确实拥有设备锁；没有进行中的退出或升级安装。
2. 设备身份、绑定版本、网络配置和账号存储可验证，恢复依据的设备与账号范围及版本仍匹配；人工扩大范围须走独立显式流程。
3. 旧本机任务已结束或被可靠隔离，旧 worker 不能继续发送冲突请求。PID 不存在、锁超时或一条记录本身都不足以单独证明。
4. 不存在需要先核对的登录、换号、接入、暂停／恢复或其他账号写操作；不能用当前快照代替原操作结果。
5. Hive 侧设备与准备保护归属满足既有规则；原归属未知时继续阻塞。需要 Hive 新协议的情况单列依赖，不虚构恢复成功。
6. 持久保存的原运行意图为运行，且未被较新的用户停止或暂停覆盖；意图缺失、损坏或矛盾时不自动恢复。停止状态只允许恢复管理能力。
7. 能以持久记录承接新的本地会话，并保留原会话与失败原因。

管理只读模式采用经审计的命令白名单；当前可能触发维护的账号刷新接口不能因为名称含“查询”就直接放行。诊断、资格检查及“重新连接”均不得隐式触发旧写操作。

恢复资格只是当时观测，不是长期通行证。所有条件在真正提交时重新验证，自动与人工入口均不能直接绕过 `StartupGate`、更新校验或写屏障。

现有 `reserveRecoveryGuard` 和 `VerifyStartup` 明确拒绝非 clean 的继承会话，普通 restore 还校验原运行意图；因此旧脏会话的自动接管仍依赖新增安全证明，不能通过改为普通手动 start 或传 `restoring=false` 绕过。仅在上述证据充分时允许受控预留，保留原记录引用；无法获得旧 worker／Hive 归属证明时继续阻塞。后续实施新增了真正的 Hive 旧代请求隔离与持久退役证明，见[补充设计](2026-11-11-session-retirement.md)；配套补丁尚未部署，当前真实账号未恢复。干净会话使用原恢复路径；旧会话证据不足时停在贡献前并保留管理与诊断能力。

### 4.3 恢复操作与崩溃窗口

沿用既有操作 ID、实例、绑定／网络／账号版本校验；补足本场景所需的持久恢复记录，不建设通用任务系统。

- 在启动副作用前，原子保存恢复 ID、原运行意图及其版本、自动／人工触发来源、设备与账号范围、原会话引用、状态版本和阶段；持久化失败则不启动。
- 本设备同一时间只允许一个恢复操作。重复提交同一 ID 查询／返回原操作；同 ID 参数变化拒绝，其他 ID 在原结果未决时拒绝。
- 恢复记录使用现有私有文件存储与设备锁；原子替换文件，记录不包含凭据。保护标记与恢复记录跨文件写入不能被假设为原子事务：中途崩溃均落入待核对，而不是可自动重试。
- App 重启或回执丢失后读取原记录；不得因为内存中的操作 ID 丢失而重新启动。已确认的成功／失败终态不改写，新的尝试另有 ID 并关联前次。
- 旧会话先经 Hive 完整退役证明结束：先持久化证明，再分阶段结束旧 scope 和 guard，最后进入正常预留路径；不以本机锁或删文件作为 clean 证据。部分保存中断沿用原证明恢复。未决业务写由原流程核对，本恢复不重放。
- 成功要求新服务状态、当前设备／账号范围和最新接单选择回读一致；无已接入账号时允许明确落入“等待接入账号”，不伪造服务运行。账号独立凭证故障继续按实际状态展示。只收到“操作已受理”不能报成功。
- 自动恢复原运行状态可能恢复接单，此规则写入产品恢复说明；不以每次弹窗为前置。原已暂停账号不得因恢复而解除暂停，恢复期间的新停止／暂停必须阻止后续不允许的准备或供给。

### 4.4 失败证据与诊断

Rust 保存此次启动尝试的失败证据，即使子进程被回收仍能读取。前端区分“当前状态”和“上次失败记录”，用启动尝试 ID／实例归属阻止旧事件覆盖新状态；不因停止就抹掉故障证据。

详情单层展示最初失败点、实际值、清理结果和原操作标识，经现有脱敏处理。失败原因不能被后来一次查询失败替换，应分别列出。

“查看诊断”在管理进程不可用时仍能展示 App 保存的启动／清理记录，并支持本地导出；不可执行的实时检查明确标注“后台不可用，未执行”。不自动上传，不混入凭据，不把通知权限告警作为本次启动故障原因。

## 6. 验收条件

| 场景 | 必须验证的结果 |
| --- | --- |
| 本次真实故障 | 显示停止与原始原因；新版启动不再次因同一旧保护状态杀掉可安全保留的管理进程 |
| 正常启动与干净退出 | 既有自动恢复行为正常，不增加常规确认弹窗 |
| 旧保护未确认，但本次尚无副作用 | 自动连接并核对；证据不足时留在只读模式，证据充分且原意图有效才准备账号 |
| 已开始工作后失败，停止未确认 | 仍执行原有严格清理，不误用启动前拒绝例外 |
| 切页、重复点击、重启及确定失败 | 不重置尝试预算、不重复提交，未决操作沿用原 ID，确定失败后不自动循环 |
| 原意图停止／缺失，或恢复期间新暂停／停止 | 停止意图不自动启动；未知意图阻塞；新选择不被历史恢复覆盖 |
| 真实子状态、数量缺失、事件乱序 | 阶段与计数来自当前操作；无可信数量不显示分数，无计时伪进度 |
| 先失败再停止／事件乱序 | 故障证据保留；新实例不采用旧状态为当前事实 |
| 查询超时、IPC 拒绝、订阅失败 | 明确失败点或未知状态，有受限查询出口，不无限显示启动中 |
| 恢复回执丢失、保存失败、阶段间崩溃 | 原记录可核对；不换 ID 重做，不误报成功或干净结束 |
| 设备被替换、锁被其他进程占用、网络版本变化 | 准入拒绝，原恢复上下文失效，不强杀其他进程 |
| 登录／换号／供给操作未决、记录损坏 | 不自动重放、不清空保护，诊断指出阻塞项 |
| 一平台暂停、一平台允许接单 | 暂停保持；允许平台按最新选择和准备条件执行，不从历史 resume 列表解暂停 |
| 待完成升级或退出与恢复竞争 | 更新标记与退出屏障不被清除，不产生第二个管理／服务 owner |
| 后台不可用的诊断页 | 本地证据可查看／导出；实时检查没有伪成功 |
| 浅／深色、最小窗口、键盘操作 | 单层详情、无溢出、正确焦点、故障信息可读 |

验证顺序：先用受控故障复现本链路并使回归测试失败，再实现；覆盖 Go 准入与崩溃点、Rust 监管／更新竞争、React 状态、真实阶段与人工处理流程，最后验证打包后的 macOS App。本轮方案反馈不是执行真实恢复的授权；实现后的自动恢复验收先使用隔离的受控数据。本轮不运行可能触发用户真实账号接单的恢复；日后真实环境验证另行明确授权与范围，不能把运行新版 App 当作无副作用测试。其他平台未实测时明确列出范围。

发布门槛：不能仅以浏览器 mock 通过、构建通过或签名通过宣称问题解决；必须有原生真实启动与停止状态展示证据，以及受控恢复成功／失败／未知结果证据。
