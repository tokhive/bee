## 背景与已核对事实

本机配对请求在 Hive 创建成功，但 Bee 校验返回网址失败，未保存到配对凭据。旧记录一直停在 `creation_unknown`。管理员查询发现对应配对已过期、未批准、未兑换，但 App 没有接口自行取得和保存这一结论。实际部署证据见[本地部署记录](../evidence/2026-11-13-local-deployment/README.md)。

初始讨论的源码基线：Hive `f208e408012bb08d257acfd858497dcc438fd010`；Bee 已安装版本 `8b5ba8027795475edb43d338caf173cf6a5a0221`。初始讨论基于后续仅增加部署证据的 `62b7cc1`；本轮工作位置与版本见末节，尚未修改产品实现。

- Hive 创建接口只有设备名和设备凭据摘要，没有跨端请求编号；每次提交都可能创建新配对。同一个设备凭据摘要可对应多笔配对。见 Hive `hive/internal/service/devices.go:25` 和迁移 `006_bee_devices.sql`。
- Hive 只保留配对 token 和配对码的摘要，不能直接取回原明文；现有配对查询需要原 token。见 Hive `devices.go:121`。
- Bee 保存了本地操作编号、原 Hive、设备秘密和提交标记，但创建请求没有将操作编号发给 Hive。创建结果未知且没有 token 时，不会重新提交。见 Bee `agent/desktop_device_recovery.go:523`、`:560`。
- Hive 的配对过期响应本身不能证明“从未兑换”：当前查询先判断过期，再判断是否已兑换。身份查询拒绝也不能证明旧配对没有创建或兑换。见 Hive `devices.go:121`、`hive/internal/service/device_auth.go:13`。
- 只查询当前记录均已过期，无法排除迟到的旧创建请求随后生效。若要结束旧操作后创建新配对，必须保证旧请求之后不会再造成冲突。
- 当前初次配对过期续建复用设备秘密，凭据恢复续建会轮换设备秘密；两者都复用本地操作编号，尚未为每次续建分别保存历史证据。见 Bee `agent/desktop_device_recovery.go:448`、`:756`。因此不能假定现有操作编号已经精确对应每次远程创建。

## 侧边讨论反馈：聚焦故障恢复

用户授权将本次讨论反馈纳入范围判断，不代表批准完整设计或开始实施。修正之前扩大范围的建议：本轮不建议增加“主动重置正常绑定”，也不提供通过清空本地记录绕过故障的方案。

| 情况 | 建议处理 |
| --- | --- |
| 绑定有效，Bee 可以正常连接 Hive | 无需重新绑定 |
| 配对结果不明确 | 先核对，已成功则恢复原绑定 |
| 原配对无法继续 | 沿用 Q4/Q5，安全结束原申请，再重新配对 |
| 凭证失效，或凭证丢失、损坏且确实无法恢复 | 提供“重新绑定 Hive”；通过 Hive 网页确认身份，安全撤销旧凭证并完成新绑定 |
| 网络不通、地址错误、版本不兼容 | 处理对应问题，重新绑定不能解决根因 |

必须区分“绑定正常可用”和“Hive 仍认为绑定有效，但 Bee 已没有可用凭证”。后者属于故障恢复，先尝试恢复，不能因服务端仍有效就判定用户无需帮助。

当前方案依赖原设备秘密核对旧申请；秘密本身丢失或损坏时不能直接套用。如何通过网页登录确认原设备、处理未完成任务及操作、替换旧凭证，并在中断后恢复，仍须补齐技术路径与验收条件。此反馈不改变 Q1～Q8，也不将尚未补齐的场景标为已覆盖。

## 凭证丢失：新增核查与当前问题

用户随后同意继续补齐此恢复设计。只读核查确认：

- Hive 只存凭证摘要，无法返回原秘密；Bee 的完整配对恢复记录可能仍保存原凭证。先核对原 Hive、身份和操作，再决定能否修复本地配置，不盲目覆盖。依据：Hive `hive/internal/repository/migrations/006_bee_devices.sql`、`hive/internal/service/devices.go:35`；Bee `agent/desktop_device_recovery.go:83`、`:488`。
- Hive 已支持登录用户明确确认并替换其当前设备，不需要旧秘密。兑换时核查任务和结算，在同一事务中撤销旧设备、创建新设备；网页确认本身不撤销旧凭证。依据：Hive `hive/internal/service/devices.go:59`、`:88`、`:180`。
- 旧设备离线不直接禁止替换，也不证明已经安全。Hive 依持久执行记录检查任务与结算；已有执行预算规则仅适用于特定的终止未知记录，不能将仍在执行或未结算的任务按超时清除。依据：Hive `hive/internal/service/device_replacement.go:59`。
- 未完成的设备排空或运行退役会阻止替换，而目前核对和收尾接口要求旧凭证。Bee 的账号操作核对也依赖旧凭证，因此“先用原接口收尾，再重绑”不能解决原凭证丢失。依据：Hive `hive/internal/service/device_drain.go:21`、`hive/internal/controller/device_drain.go:36`；Bee `agent/desktop_account_selection.go:166`、`agent/desktop_session_retirement.go:119`。
- 配置无法解析、恢复记录损坏、已登记 profile 目录丢失会在普通配对入口之前失败，恢复入口须独立处理这些读取失败，并保留原文件。依据：Bee `agent/state.go:22`、`agent/desktop_device.go:77`、`desktop/src-tauri/src/profiles.rs:380`。

## 已确认边界

- 用户一次发起“重新配对”，Bee 记住这一意图：先安全结束旧配对，再生成新配对码。关闭或重启后先核对进度，再继续同一次操作；若发现原绑定已成功，则恢复原成功结果。
- 新建、重建配对前检查支持情况；不支持时明确引导升级 Hive。已有正常绑定沿用现有连接；仍能安全完成的旧配对或身份核对不因版本门槛被阻断。取舍是旧版 Hive 的用户须先升级，才能生成新的配对码。
- 原配对核对中，记录互相矛盾、无法确定应恢复哪个绑定时，暂停自动推进，保留证据并提供不含秘密的诊断摘要，交由 Hive 管理员核实。多笔尚未完成且可以安全一并结束的旧配对，本身不算这种冲突。后续重绑范围还包括任务完成或结算证据不足的人工处理边界，见末节与最小技术契约。

无法连接 Hive、核对结果不足时继续保留待核对状态，不凭超时认定旧配对已结束。关闭弹框不取消远端配对；取消父切换后保留原结果核对，但不能自动新建 B 的配对或恢复前进 B。这些是既有安全约束的应用，不作为新选择重复确认。

完整的待确认方案见[配对恢复设计](2026-11-13-pairing-recovery.md)。其中协议、存储和验收部分是基于源码核查提出的方案，尚未视为用户已批准实现。

## 2026-11-16：批准的 8 点重绑方向

用户在逐项说明已有能力、建议新增能力和未决边界后回复“批准”。批准涵盖以下方向及 Q9 受限权限，不把此前所有协议、表结构和接口草案一并视为已批准，也不授权操作真实 App、撤销真实绑定或修改数据库。

1. **入口不依赖正常配置**：配置损坏、凭证或 profile 目录丢失时，Bee 仍提供“重新绑定 Hive”。本地地址也丢失时由用户确认地址，保留剩余记录。
2. **优先恢复可验证的原绑定**：Bee 检查可信恢复记录并向 Hive 验证凭证，有效则恢复。网络、地址、版本问题处理实际原因，不以反复重绑替代。
3. **网页受限恢复授权（Q9）**：用户登录原设备所属的 Hive 账号并明确确认旧设备，授权 Hive 服务端在没有旧设备凭证的情况下处理本次恢复阻塞。已有网页配对和替换本来就不要求旧设备凭证；新增的是遗留操作处理权限。设备凭证由 Bee 自动生成、保存和携带，不是 Hive 密码或 AI 账号密钥。
4. **处理遗留操作**：Hive 核对停止接单、运行退出和旧配对的实际结果；确认已完成的记录结果，能继续的继续，确认可结束的结束。不能仅清空状态绕过任务和结算。
5. **等待旧任务及结算，不强制中断**：替换等待阶段不再向旧设备派新任务。已有任务等待完成；旧 Bee 无法连接时，须核查现有超时、失败判定与结算路径。等待时长未核实，可能卡住；任何新增强制终止选择须单独批准。
6. **隔离旧绑定**：沿用撤销旧设备并创建新设备的事务，核查并补齐旧连接、已经通过鉴权的迟到请求处理，保留任务与账目，不把状态撤销当成隔离完成。
7. **同一次重绑可续办**：Bee 发送前保存必要信息，Hive 保存可核对结果。回包丢失、重启、本地保存失败继续原结果；并发替换核对冲突，不误撤销后来设备。
8. **阻塞具体可见**：Bee 说明等待对象和下一步；可以续办的不要求重走全程。无法关联旧请求或归属证据矛盾时保留证据并提供管理员诊断信息，不承诺一键自助成功。

表达约定：明确区分 Bee、Hive 网页、Hive 服务端及用户操作；不用含糊的“系统”掩盖职责；等待和收尾须说明对象、后果与未核实边界。正常绑定不主动重置，不新增重置中心或通用历史恢复平台。重绑完成后用户重新选择 AI 账号，不自动开始贡献。
