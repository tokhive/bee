# 配对结果待核对：恢复能力讨论

状态：访谈中。记录已确认结论和下一轮问题；不是已批准设计，不授权实施。

## 背景与已核对事实

本机配对请求在 Hive 创建成功，但 Bee 校验返回网址失败，未保存到配对凭据。旧记录一直停在 `creation_unknown`。管理员查询发现对应配对已过期、未批准、未兑换，但 App 没有接口自行取得和保存这一结论。实际部署证据见[本地部署记录](../evidence/2026-11-13-local-deployment/README.md)。

源码基线：Hive `f208e408012bb08d257acfd858497dcc438fd010`；Bee 已安装版本 `8b5ba8027795475edb43d338caf173cf6a5a0221`。本次讨论基于后续仅增加部署证据的 `62b7cc1`，尚未修改产品实现。

- Hive 创建接口只有设备名和设备凭据摘要，没有跨端请求编号；每次提交都可能创建新配对。同一个设备凭据摘要可对应多笔配对。见 Hive `hive/internal/service/devices.go:25` 和迁移 `006_bee_devices.sql`。
- Hive 只保留配对 token 和配对码的摘要，不能直接取回原明文；现有配对查询需要原 token。见 Hive `devices.go:121`。
- Bee 保存了本地操作编号、原 Hive、设备秘密和提交标记，但创建请求没有将操作编号发给 Hive。创建结果未知且没有 token 时，不会重新提交。见 Bee `agent/desktop_device_recovery.go:523`、`:560`。
- Hive 的配对过期响应本身不能证明“从未兑换”：当前查询先判断过期，再判断是否已兑换。身份查询拒绝也不能证明旧配对没有创建或兑换。见 Hive `devices.go:121`、`hive/internal/service/device_auth.go:13`。
- 只查询当前记录均已过期，无法排除迟到的旧创建请求随后生效。若要结束旧操作后创建新配对，必须保证旧请求之后不会再造成冲突。
- 当前初次配对过期续建复用设备秘密，凭据恢复续建会轮换设备秘密；两者都复用本地操作编号，尚未为每次续建分别保存历史证据。见 Bee `agent/desktop_device_recovery.go:448`、`:756`。因此不能假定现有操作编号已经精确对应每次远程创建。

## 本轮已确认

| 问题 | 用户确认 |
| --- | --- |
| Q1：处理当前旧记录还是只防止以后发生 | 同时覆盖已卡住的旧记录，以及以后的响应丢失、返回校验失败、App 重启 |
| Q2：覆盖哪些入口 | 首次配对、重新绑定、切换 Hive 时准备目标 Hive，共用恢复能力 |

沿用已确认约束：未决写入不能通过换编号、换 Hive 或删除配置绕过；各 Hive 的凭据和恢复记录独立；网页登录仍确认设备归属与替换；配对完成不自动接入账号或开始贡献；取消切换不冒充远端配对已取消。

## 决策树与当前待确认事项

```text
Q1 旧记录及未来新请求都覆盖（已确认）
├─ 未来新请求
│  └─ Q3 是否优先自动核对并继续原配对（本轮待确认）
│     └─ 后续：原请求身份、终态、证据保留及兼容边界
└─ 已丢失配对凭据的旧记录
   └─ Q4 尚未完成时，是否允许用户主动结束旧配对再生成（本轮待确认）
      └─ 后续：识别旧请求、关闭迟到写入、已成功结果与冲突处理

Q2 全部配对入口统一覆盖（已确认）
└─ 后续：按本地 Hive 及配对尝试隔离、目标配对与切换取消的协调
```

Q3 推荐：未来响应丢失或 App 重启时，Bee 自动核对并尽量继续原配对；只有 Hive 确认已不能继续，才提示用户重新生成。新配对仍需用户明确发起。

Q4 推荐：对于旧记录无法取回原配对凭据且尚未完成绑定的情况，允许用户主动结束旧配对，再重新生成，不强制等待自然过期。必须由 Hive 确认原结果并保证旧请求之后不能再生效；已经成功绑定时保留成功事实，不能按“未发生”处理。这一推荐尚未获用户确认。

## 技术栈与范围

沿用现有 Bee Go 核心、Rust/Tauri 桌面协调、React/TypeScript 页面，以及 Hive Go 服务和 PostgreSQL。当前构建基线为 Go 1.27.3、Rust/Cargo 1.94.0、Node 24.22.1；其余版本继续由现有仓库锁文件固定。不引入新服务或外部平台作为当前讨论前提；跨端恢复协议和持久数据结构尚待决策。
