# Bee 桌面安装与更新说明

当前为发布准备文档。正式候选版本、生产下载地址和完整签名材料尚未提供，[八组合安装与更新验收](release-validation.md)仍为 pending。下列步骤用于候选验收和正式发布后的操作，不表示当前已有经过验收的正式下载包。

Bee 安装包自带匹配的 Bee，无需安装 Go、Rust 或执行 Bee 命令。正式名称为 Bee，应用标识沿用 `dev.tokhive.bee`，升级继续使用既有用户数据路径。

## 支持范围

| 系统 | 架构 | 安装包 | 本次原生验收 |
| --- | --- | --- | --- |
| macOS 13 及以上 | arm64／x64 | DMG | 两组合待验收；必须覆盖 macOS 13.x |
| Windows 10 22H2 | x64 | NSIS | 待验收 |
| Windows 11 | x64 | NSIS | 待验收 |
| Ubuntu 22.04 | x64／arm64 | AppImage | 两组合待验收 |
| Ubuntu 24.04 | x64／arm64 | AppImage | 两组合待验收 |

以上为已批准的八组合目标，当前没有扩大到其他 Windows 架构、Linux 发行版或安装格式。较新 macOS、Windows Server 和 Linux 容器结果不能补齐目标系统验收。

## 安装前准备

先从正式发布地址选择与系统和 CPU 架构相符的包，核对该版本发布说明、SHA-256 清单和签名验证结果。当前正式地址及清单待补齐；请勿把测试源或历史 Bee Dev／demo 包当作本次正式版本。

Bee 通过已安装的官方 Codex／Claude 客户端检测已有登录或发起官方登录。两者均需独立安装，受支持版本应以本候选的验证记录为准；Bee 安装包不包含这些官方客户端。缺少客户端、版本不支持、权限拒绝或来源损坏时，须先按实际错误处理，再重新检测。密码、验证码和授权交互在官方界面完成。

文件来源支持三端；OpenAI 的 Keyring 与 Claude 的 Keychain 来源按当前实现仅在 macOS 支持。来源切换、权限拒绝和损坏须分别显示实际结果；不支持的存储方式应明确说明不支持，不能显示为未登录。Ubuntu 验收还须分别覆盖桌面有托盘／无托盘时的窗口找回。

已有官方登录不会自动接入贡献。完成设备配对后，在 AI 账号页核对来源和账号，确认选择，再点击“开始贡献”。暂停、恢复与换号按平台分别显示结果；换号完成后保持暂停，需再次明确恢复。真实贡献仅使用已授权账号和流量范围。

## 安装

1. macOS：打开对应架构 DMG，将 Bee 拖入 Applications，再从 Applications 启动。先核对 Developer ID、公证及票据验证记录。遇到系统验证失败时保留具体错误，使用可信包处理，不绕过签名检查。
2. Windows：以普通用户运行对应 NSIS 安装包，使用当前用户安装路径，按提示准备 WebView2。核对 Authenticode 签名及发布者。安装后从已安装位置启动 Bee。
3. Ubuntu：将对应架构 AppImage 保存到当前用户可运行的位置，按系统要求赋予执行权限，再在真实桌面会话启动。若系统缺少 AppImage／FUSE 运行依赖，按候选验证记录补齐实际缺项。容器解包或 Xvfb 启动只作辅助诊断。

首次启动应保持未开始贡献，不覆盖既有 CLI／官方登录文件，也不终止外部 Bee。包内 Bee 必须与 App 的版本、源码、系统及架构配套；应用不从 PATH 任意选择同名 Bee。若实际表现不符，保留错误及诊断记录，不将安装成功标作主流程完成。

## 包校验

使用该正式版本提供的 SHA-256 清单核对下载文件，例如：

```sh
# macOS
shasum -a 256 <下载的DMG>
# Ubuntu
sha256sum <下载的AppImage>
```

```powershell
# Windows PowerShell
Get-FileHash -Algorithm SHA256 -LiteralPath '<下载的NSIS安装包>'
Get-AuthenticodeSignature -LiteralPath '<下载的NSIS安装包>'
```

将实际摘要与同一版本、渠道、平台、架构的发布清单逐项比较。SHA-256 不能代替签名。macOS 还须核对应用的 Developer ID、Gatekeeper／公证票据结果；Windows 签名状态须有效并匹配正式发布者；更新资产必须通过固定生产公钥验签。当前正式摘要、公钥身份、发布者及公证材料均待随候选补齐。任何一项不符都停止安装或更新。

## 检查与安装更新

1. App 启动后后台每日最多检查一次；也可在设置中手动“检查更新”。检查失败保留当前版本，并显示实际原因与最近检查时间。
2. 有更新时核对版本、平台与变更说明，下载后等待签名验证完成。下载进度未知时不代表已完成。检查或下载不会批准安装。
3. 明确选择“退出并安装”后，App 保存运行意图与未决状态，停止自己管理的运行并回收子进程、释放其配置锁，再交给平台安装流程。此操作可能中断当前任务。
4. 新版本启动后，核验包内 Bee、设备配对、账号选择、暂停状态、偏好及未决操作。只有真实启动与恢复成功才显示更新完成。

受控更新地址、公钥、渠道及版本在构建时固定。界面不接受任意下载地址或可执行路径。签名不符、架构不符、下载中断、磁盘／权限问题、重复安装或回收失败时停止本次安装，并显示实际失败点。若运行已停止但安装失败，界面须显示停止状态，不能声称仍在贡献。保留可信旧包及原数据，再按错误处理后重试。

## 数据与已知限制

更新前由 S1/S2 的配置迁移保护原件，用户数据位于系统用户配置目录，账号状态不写入安装目录。更新不复制官方 token，不覆盖 CLI／官方登录配置。新格式无法被旧程序读取时，旧程序明确拒绝，不静默清空。

卸载应用不会自动清除设备配对、官方客户端登录或 CLI 配置。安装失败不承诺任意断电点自动回滚，也不承诺等待全部任务结束；用户确认退出安装时可能中断任务。暂停不等于终止已有请求。

当前 S1-T6 owned 退出／恢复、S2 偏好迁移与设置页整合、授权真实账号主流程、生产签名资源及八组合原生验收尚未齐备。因此本文件尚不能作为正式发布完成说明。发布前须将真实版本、客户端版本、签名身份、下载地址及剩余限制补入[验证记录](release-validation.md)，确认 P1–P6 后再按明确发布授权交付资产。
