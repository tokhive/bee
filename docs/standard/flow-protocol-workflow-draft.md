# 流程与协议梳理工作流（非正式草案）

> **状态：非正式、试行，仍需打磨。**
> **启用条件：仅在用户明确要求采用本工作流时，才在用户指定的任务范围内遵循。**
> 放入 `docs/standard/`、被索引引用或被智能体读取，均不构成启用；一般开发、排障、审查任务不自动触发。保存或编辑本文也不等于要求按本文启动业务梳理。
> 本文不替代已有正式规范。后续是否调整、推广或转为正式规范，由用户明确决定。

## 目的与产出

让用户能够看懂、质疑和验收流程，让智能体用代码和运行证据说明每个结论。重点解决局部测试通过、某个时刻恢复正常，但跨模块流程或重启恢复仍不完整的问题。

每轮围绕一条用户路径工作，维护三类相互对应的材料：

| 材料 | 回答的问题 |
| --- | --- |
| 流程图 | 用户经过哪些步骤，哪些模块协作，失败后走哪里？ |
| 行为与协议约定 | 谁负责、什么算完成、状态如何转换、记录如何收尾？ |
| 验收清单及证据 | 哪个场景验证了哪条约定，结果是什么，哪里尚未验证？ |

材料可按规模合并，复用已有文档并链接源码，避免重复维护。业务规格、阶段记录和证据按仓库现有文档与档案规则存放；本文只描述工作方法。

## 1. 还原实际流程

先读取用户已确认的行为、相关设计、实际代码和运行证据。记录核对的仓库、worktree、分支、提交及实际运行版本；区分源码现状与运行程序，不能默认二者一致。

以用户路径组织流程图，每一步写清：

- 谁触发，谁执行，谁判定完成。
- 涉及哪些本地命令、进程间调用和 Hive 接口。
- 哪些记录会落盘，如何关联设备、账号、操作和运行实例。
- 成功、明确失败、超时或响应丢失分别转到哪里。
- 进程退出、崩溃、重启后依据什么继续。
- 用户看见什么、能做什么，哪些读取和恢复自动进行。

结论标注为“已核实”“推断”或“尚未查清”，并附证据入口。设计文档说明预期，源码说明实现，运行记录说明某次实际发生的事；三者分别核对。

**阶段完成条件：**选定路径的正常、失败及重启分支均有对应节点；未查清的边界显式列出。先完成事实梳理，再提出修复，不能靠补丁替代对原流程的解释。

## 2. 明确行为与协议约定

对路径涉及的每个事务和状态，明确以下约定，并列出实际实现与预期行为的差异：

| 约定 | 必须回答的问题 |
| --- | --- |
| 责任归属 | 谁拥有这个状态，谁有权推进，其他模块如何获知变化？ |
| 受理边界 | 什么证据证明操作尚未受理、已经受理或已经执行？ |
| 完成条件 | 哪个结果或回执证明成功、失败或取消？ |
| 结果未知 | 什么情况允许进入 `unknown`，可能发生了什么副作用？ |
| 重试与核对 | 可以重试原操作、创建新操作，还是只能查询原结果？ |
| 持久化与关联 | 哪些字段跨重启保留，如何识别旧设备、旧实例或旧操作？ |
| 收尾 | 何时成为终态，何时退役、归档或清理，由谁负责？ |
| 跨事务衔接 | 一个事务完成后，谁重新评估依赖它的阻塞条件？ |

每个阻塞状态都要有解除条件和负责解除的模块；“先阻止执行”不能代替恢复路径。每种非终态都要说明如何结束，无法自动结束的情况要说明人工处理所需证据和操作。

尤其要区分“前置检查明确拒绝”和“操作可能已执行但结果未知”。`operation_id` 为空本身不能证明没有副作用；结论须追溯到实际受理和执行边界。不得仅为解除阻塞而删掉未决记录或将其改成成功。

**阶段完成条件：**所选路径上的状态转换、完成依据和恢复责任均已列明；差异与未决问题有编号，后续设计、修改和验收可引用。

## 3. 确认用户可见的行为

智能体将差异转成具体场景，说明当前行为、建议行为、影响和取舍。用户确认产品行为及需要裁决的选择；智能体承担技术论证、内部组织和验证工作，不把读源码与发现遗漏的责任交给用户。

例如：“首次打开尚未配对，随后配对成功；应该自动继续哪些步骤，哪些动作需要明确确认，关闭再打开后应出现什么？”

沿用已有确认，不反复询问相同原则。设计和实现的授权范围遵循当前用户指令及仓库既有规则；仅启用本文不代表用户批准所有后续设计、状态变更或实现。

**阶段完成条件：**影响本轮实现的产品行为和重要取舍已有明确依据；待裁决项不会被隐藏在实现细节中。

## 4. 修复并验证完整路径

先建立能捕获所述问题的验证，再修改实现。测试应覆盖实际跨模块调用、持久化记录和恢复过程，不能只在过浅的模拟边界复述实现。

将每项差异对应到代码修改及验收场景；本轮修改涉及的正常、失败、结果未知、退出和重启分支一起核对。先验证一条完整路径，再扩展范围。

对于启动与配对路径，可采用以下场景作为梳理起点，按已确认范围补充：

1. 未配对启动，随后配对成功。
2. 配对期间退出，再次打开。
3. 启动被明确拒绝后，前置条件恢复。
4. 操作已经受理但响应丢失，核对时不重复执行。
5. 正常运行、退出、重新打开。
6. 原先暂停的账号在恢复后保持暂停。

除自动化测试外，验证真实 App 的相关交互及重启行为，并核对实际记录和 Hive 状态。真实环境中的账号选择、开始或停止贡献、解除暂停等动作遵循既有授权要求。无法执行的验证记录为“未完成”，说明原因和影响范围。

**阶段完成条件：**原问题有验证结果；本轮受影响的完整路径有证据；剩余缺口已明确披露，不能用局部通过推导整体通过。

## 5. 凭证据交付

交付内容与前述材料逐项对应，至少说明：

- 原来哪条流程错误，改后是什么行为。
- 修改了哪些状态转换和协议约定，对应哪些代码。
- 实际验证了哪些场景、环境及版本，结果和证据入口在哪里。
- 哪些仍未验证、存在什么风险，结论的适用范围是什么。
- 修改所在的仓库、worktree、分支和提交；未提交项单独注明。

“编译通过”“测试通过”“当前恢复正常”各自只支持其直接验证的结论，不能单独证明整个生命周期正确。完成后按仓库既有规则提交、归档，并同步三类材料。

## 试行与后续打磨

Bee 的首次试行建议聚焦“启动—配对—恢复—退出—重启”，梳理 Rust、Go 与 Hive 的责任边界，以及设备配对记录和启动恢复记录之间的关系。该建议不构成自动启动任务的指令。

试行结束后记录：用户能否据此理解并质疑流程、哪些步骤实际发现了遗漏、哪些材料重复或成本过高、验收还遗漏了什么。根据实际反馈调整本文；在用户明确要求转正前，始终保持非正式、按需启用状态。
