# Bee Linux 安装后设置与启动向导设计

## 背景与批准状态

已有安装脚本会安装 Bee、生成并启用系统级 systemd 服务，但首次使用仍要求用户手工运行前台 Bee、配对、停止进程，再启动服务。用户已明确批准推荐方案：安装后进入交互向导，先完成配对和账号选择，再直接启动后台服务；已有配置则减少步骤，运行中的系统服务仅在用户同意后重启，无交互终端时跳过向导。

本 spec 将已确认设计落盘，并补齐上一阶段缺失的安装与自启动设计说明。用户已要求实现并沿用现有 PR，不重复申请同一方案的执行许可。

## 技术栈与选型

| 技术 | 用途与理由 | 版本要求 | 状态 |
| --- | --- | --- | --- |
| POSIX sh | 扩展现有安装脚本，支持 `curl ... | sh` | 沿用 `/bin/sh` | 沿用，已确认 |
| systemd | 系统级后台进程及开机启动，运行身份为安装用户 | 243+，沿用 ExecCondition | 沿用，已确认 |
| 已有 Bee CLI | `bee login` 配对、`bee setup` 选择账号；不添加新的运行协议 | 使用已支持这两个命令的发布版本 | 沿用，已确认 |
| Python 3 标准库 | 安装回归测试及真实伪终端交互测试 | 与现有测试一致，3.9+ | 沿用，已确认 |
| GitHub Actions、ShellCheck | Linux 原生验证及脚本静态检查 | 沿用仓库 CI | 沿用，已确认 |

不增加运行时依赖。备选方案是安装后直接执行现有 `bee start`，但它会持续占用终端，不能消除前台进程到后台服务的手动切换；因此采用用户已批准的拆分命令方案。

## 安装与服务基础行为

- Linux 默认写入并启用 `/etc/systemd/system/tokhive-bee.service`，`User=` 为安装用户；`HOME`、配置目录、PATH 及显式设置的官方客户端目录沿用安装环境。
- 仅管理员操作使用 sudo；拒绝以 sudo 运行整个安装脚本而误用 root 的配置。
- 保留下载校验、原子替换、自定义安装路径、托管 unit 标记、用户手写或链接 unit 保护、旧用户级服务迁移检查。
- `BEE_INSTALL_SERVICE=0` 仅安装二进制；macOS 继续仅安装二进制。
- 服务仍执行 `bee run`，缺少设备或出口配置时跳过，异常退出等待 10 秒再重试，正常退出不重启。

## 向导入口与终端

- Linux 服务安装成功后，默认尝试向导；新增 `BEE_INSTALL_INTERACTIVE=0` 显式关闭，默认 `1`，只允许 `0`、`1`。
- 仅当输出连接终端、且存在可读写的控制终端时进入。无终端或显式关闭时只安装并输出手动设置、启动、状态和日志命令。
- 从 `/dev/tty` 读取用户和 `bee setup` 的答案，不能把 `curl ... | sh` 的脚本输入当成答案。原始脚本 stdin 保持完整。
- 首次设置/启动问题默认为是；重启运行中服务的问题默认为否。无答案、EOF 或明确拒绝时保留安装结果并退出向导，不启动或重启。
- 无效的 yes/no 答案重新询问；Hive 地址不能为空，不将输入作为 shell 源码执行。

## 服务状态与交互行为

向导从 systemd 读取实际 `ActiveState`，读取失败保留底层诊断并停止，不能把无法读取状态解释成未运行。

| 状态 | 行为 |
| --- | --- |
| active | 提示服务正在运行；询问是否重启以应用本次安装，默认否；不重新配对或改写账号选择 |
| inactive / failed | 询问是否设置并启动；同意后进入以下设置流程 |
| activating / reloading / deactivating | 提示当前过渡状态，保留现有进程，不执行设置或进程操作 |
| 未知状态 | 明确报告实际状态，停止向导 |

设置流程：

1. 设备配置不存在时询问 Hive 地址，调用绝对路径的 `bee login --config ... --hive ...`。
2. 设备配置已存在时调用 `bee login --config ...`，由已有 CLI 验证身份或恢复未完成的配对，不在 shell 中解析 JSON，也不默认把“文件存在”当成配对完成。
3. 出口配置不存在时调用 `bee setup --config ... --egress-config ...`；保留其逐账号授权问题，不传 `--yes`。已有出口配置不重新选择账号。
4. 任一步失败即停止后续步骤，保留二进制、已生成的配置及底层错误；未成功配对或设置时不能启动服务。已有配置的在线身份验证失败时也不能伪报成功，用户仍可按提示手动启动服务等待网络恢复。
5. 检查两份配置已存在，再执行 `systemctl start tokhive-bee`；用户确认重启时执行 `systemctl restart tokhive-bee`。
6. 操作返回后再检查 `ActiveState=active`，才报告服务已启动，并展示状态和日志命令。此状态只表示服务进程已启动，不承诺 Hive 已连接或账号已接单。

普通前台 Bee 使用配置锁；向导复用 `bee login` 的同一锁机制，遇到运行中的前台进程会保留 CLI 的锁冲突诊断并停止，不杀进程、不启动另一份、不靠进程名称猜测身份。

## 失败与兼容边界

- 安装、状态读取、配对、账号设置、服务启动或重启分别报告失败操作、相关路径或实际状态；命令退出失败时保留原始输出和退出码。
- 向导失败会返回非零，但不撤销已经完成的安装，不删除凭证，不自动重试。
- 原有配置无法被 CLI 接受时不覆盖修复；提示保留配置并按原始诊断处理。
- 活跃服务不会因重跑安装脚本而自动中断。没有终端时也不自动开始账号设置或进程操作。
- 本次不新增服务管理 CLI、后台守护实现、启动参数持久化协议或 macOS 启动向导。
