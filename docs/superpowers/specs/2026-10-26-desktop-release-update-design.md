# Bee 桌面：安装、更新与发布验收

日期：2026-10-26。状态：**spec 已获用户整体批准；对应实施 plan 已获执行授权，按 S1→S2→S3 顺序推进**。本文为 S3，承接[S1 账号与运行](2026-10-26-desktop-account-runtime-design.md)、[S2 诊断与日常体验](2026-10-26-desktop-diagnostics-experience-design.md)。[对应实施计划](../plans/2026-10-26-desktop-release-update.md)已获执行授权；本轮不发布安装包。

## 1. 用户最终得到什么

用户下载对应系统安装包即可安装 Bee，无需安装 Go／Rust 或运行 Bee 命令；App 内能检查版本、下载更新、确认退出并安装。更新后设备配对、账号选择、暂停和偏好保留。登录官方 AI 账号仍需要 S1 已确认的官方客户端，不将其误写成 Bee 已内置官方客户端。

交付的是来源可核验、签名正确、经过真实安装和主要操作验收的正式包。构建成功、浏览器测试通过或已有开发包都不能单独代表发布完成。

## 2. 继承范围和当前证据

以[当前需求](../../../../../docs/discussions/2026-10-21-bee-desktop-requirements.md#当前有效范围2026-10-26)及相邻决策记录为准。旧 P0/P1 缺口中与窗口、系统权限、真实官方来源、进程回收、安装及目标平台有关的部分继续验收；旧 Hive 用户登录、五页资金界面、独立市场列表、完整移除和等待任务退出不再作为交付门槛。

现有[桌面配置](../../../desktop/src-tauri/tauri.conf.json)为 Bee Dev／`dev.tokhive.bee`，已有 DMG、NSIS、AppImage 配套打包；[原生 CI](../../../.github/workflows/desktop.yml)及 hosted 工作流提供多平台开发包和来源证据。当前 ad-hoc 签名、demo 包和容器显示检查不能替代正式签名、真实桌面或安装验收。已有记录见[底座验证](../../desktop/p0-validation.md)和[页面验收](../../../desktop/docs/p1-acceptance.md)。本稿不改写历史测试结果。

| 用途 | 技术／版本 | 状态与理由 |
| --- | --- | --- |
| App 与 Bee | 沿用 S1/S2 的 Go、Rust、Tauri 2.12.5、React、锁文件和单仓库工程 | 已确认；一个发布版本绑定同次构建的 App 和内置 Bee |

| 托管 | 复用现有 GitHub 构建／Release 基础，提供 HTTPS 静态更新清单与包资产 | 已随本稿获批；不增加 Hive API、数据库或账号会话 |
| 原生签名 | macOS Developer ID 签名及公证、Windows Authenticode、Tauri 更新签名 | 已确认正式发布要求；密钥仅在受控构建环境，不进入仓库或前端 |
| 名称与应用身份 | 正式显示名称 Bee；首版沿用现有 `dev.tokhive.bee` 和已有用户数据路径 | 已随本稿获批；避免为改标识引入重复安装身份和数据迁移；Dev 字样不进入正式标题 |

更新服务比较：静态清单及现有包托管能完整实现检查、签名验证和下载，不需要新增业务服务，推荐采用。通过 Hive 新建更新接口也能实现，但增加后端维护和部署依赖，不符合当前边界。仅提示手动下载不覆盖已确认的 App 内安装更新目标，不作为完成方案。

生产与 demo 构建明确区分；正式包使用真实原生入口，不允许通过环境遗漏切入 demo。更新源、发行渠道、版本、更新公钥和目标包类型作为受控构建输入固定，用户不能从前端指定任意更新地址或任意可执行路径。

正式发布前需要准备的资源：发布仓库／HTTPS 资产地址、macOS 开发者签名与公证凭据、Windows 签名身份、更新签名密钥、目标原生测试环境。先把实现和本地／受控更新源验证准备好，再对缺少的具体资源说明用途及接入位置；无需向 agent 粘贴秘密。资源未就绪时可完成代码与候选包，不能声称生产发布完成。自签名测试只能标为测试证据。

## 4. 安装、版本与本地数据

macOS 支持从 DMG 拖入 Applications 后启动；Windows 使用当前用户安装路径和 NSIS 流程；Linux 提供当前用户可运行的 AppImage 及明确启动说明。安装包自带匹配的 Bee，校验平台、架构、来源与签名，不从 PATH 捡任意同名 Bee。

所有桌面用户数据保持位于现有系统用户配置目录：设备凭证文件由既有配对模块负责，账号选择及未决操作由 S1 管，普通偏好由 S2 管；日志遵循 S2 的容量和脱敏规则。安装目录不保存可变账号数据，更新不能复制官方 token 或覆盖 CLI 文件。

S1/S2 必须提供显式配置版本和原子迁移；升级前检测可读性并保留受保护的迁移前数据，失败不得覆盖原件或继续自动贡献。重启先核验设备、选择与未决动作，再按 S1 的运行意图恢复；换号后暂停、主动暂停和用户停止状态不得丢失。

卸载应用不自动删除设备配对、官方客户端登录或 CLI 配置；不增加一键注销／删除账号功能。旧程序不能读取新格式时应明确拒绝，不能静默清空；不承诺自动回滚数据格式。安装失败的恢复路径是保留可用旧包、原数据和准确错误，再重试或使用可信安装包处理，不声称任意断电点都能自动回退。

## 5. 检查与安装更新

1. App 启动后在后台检查，另有“检查更新”按钮；失败保留当前可用版本。后台检查每日最多一次，手动检查可重试，界面显示最近检查时间和具体失败原因。
2. 有新版本时显示版本、目标平台和变更说明；检查或下载不等于批准安装，不修改配对或贡献状态。只接受受控 HTTPS 清单和匹配当前系统／架构／渠道的更新。
3. 下载完成后校验更新签名和包身份；签名失败、目标不符、下载不完整或空间不足时停止，保留现有版本。Hash 用于来源核对，不能替代签名。
4. 用户明确选择“退出并安装”，说明可能中断当前任务。先冻结新的运行／账号操作，持久保存运行意图及已发生操作的未决状态，再调用 S1 的 owned 停止路径。
5. 确认 owned 运行停止、管理子进程回收及其配置锁释放后，交给 Tauri 的平台安装流程。App 的单实例保护保持到安装交接后的实际退出，不能提前开放第二实例来启动旧版本贡献。回收失败时不继续安装，也不通过终止外部 Bee 解决。
6. 新版本启动后核验包内 Bee 与协议能力、迁移数据、恢复界面及此前运行选择。只有真实启动与恢复成功才能在新版本显示更新完成；安装器返回成功本身不证明完整恢复。

没有可信任务数时不能显示“当前无任务”；本稿没有等待任务结束、临时停止派发、取消排空等服务端流程。未决换号等操作允许带着原记录退出，重启后继续核对，不能以更新为由重新提交。安装前取消保持当前 App；已停止但安装失败时显示实际停止状态，不能假装仍在贡献。

更新操作由 Rust 的固定命令管理，S2 设置页消费检查／下载／验证／待确认／退出／安装失败等状态；长操作有可观察进度和错误证据，不占住普通短请求。拒绝重复安装和迟到回执。远程清单不能执行命令、注入前端 HTML 或改变凭证来源。

## 6. 三端验收矩阵

| 目标 | 必需的原生验证范围 |
| --- | --- |
| macOS 13+，arm64 与 x64 | 最低支持版本及相应架构的真实安装、签名／公证、官方来源权限、托盘、窗口找回、退出回收和升级 |
| Windows 10 22H2 与 Windows 11，x64 | NSIS 安装、签名、WebView2、官方来源及登录、通知／自启、托盘、配置保护和升级 |
| Ubuntu 22.04 与 24.04，x64／arm64 | AppImage、实际桌面及所需运行环境、官方来源、通知／自启、托盘有无两种情况、窗口找回和升级 |

共沿用八个 OS／架构验收组合，不扩大到新平台。官方来源按真实可支持的平台类型验证：文件／Keychain／权限拒绝／损坏／来源切换；不把不支持的存储方式显示成未登录。Linux 容器或 Xvfb、Windows Server、较新 macOS 的测试结果只说明它们直接覆盖的条件，不替代目标系统证据。

证据绑定源码提交、构建模式、OS／架构、App 与 Bee 版本、包哈希／签名、测试步骤及结果。旧证据只在相关代码、配置与包路径仍适用时复用；不为每次纯文档修改重新构建所有历史版本，不用旧包截图给新产品功能打勾。

功能开发无需等待所有平台机器；完成 S1/S2 后集中使用当前候选版本验证目标矩阵。有缺失环境时标明未验证平台和具体剩余步骤，不能以 CI 构建成功抹去，也不让它变成重复重做其他平台的理由。

| 编号 | 必须证明的结果 |

| P1 安装与来源 | 每目标包可按普通用户流程安装启动，包内 Bee 来源匹配；首次启动不自动开始贡献、不覆盖已有配置或终止外部 Bee |
| P2 主流程 | 已有登录／官方登录 → 选择账号 → 明确贡献 → 暂停／恢复 → 换号后暂停 → 断网与重启恢复，均使用真实原生页面；两平台各有证据 |
| P3 日常使用 | doctor、日志导出、代理、语言主题、自启、通知、关窗和找回在安装后的路径工作；权限拒绝和导出失败准确显示 |
| P4 更新正向 | 两个配套签名候选版本完成旧版检查、下载、退出安装、新版启动、数据保留及运行恢复；实际路径覆盖各包格式 |
| P5 更新失败 | 错签名、错平台／架构、下载中断、磁盘／权限失败、重复安装、回收失败、新配置旧程序不可读均不破坏原数据或假报成功 |
| P6 发布资料 | 版本说明、支持平台、安装和更新步骤、所需官方客户端、已知限制、包校验与签名证据完整；不宣传资金／完整移除／等待退出功能 |

验证优先运行受影响单元和集成测试，再做匹配的原生包验收。重放回归仅由代码、配置变更或真实失败触发，不重复制造无关耗时。自动测试用合成来源／本地 Hive 替身／受控签名更新源；真实平台登录及受控贡献需要明确的测试账号和操作授权，提前说明具体工具及系统权限，不索取密码或 token。

正式包及更新资产准备完成后按用户届时的明确发布授权执行；已获得的具体授权不重复询问。本次 spec 审阅不等于已发布或授权向外部上传。公开发布前证据必须证明 P1–P6，缺签名资源或目标环境应报告具体阻塞，不能以隐藏功能或跳过平台改变交付范围。

## 8. 三份 spec 的执行顺序和完成含义

| 顺序 | 用户可见里程碑 | 后续依赖 |
| --- | --- | --- |
| S1 | 已有账号及官方登录都可接入，真实运行贡献，能换号和恢复 | 输出真实状态、停止能力和账号数据规则供 S2/S3 使用 |
| S2 | 日常诊断、代理、日志、提醒、偏好、自启和窗口体验可用 | 消费 S1；设置页给 S3 留版本／更新接入点，不自己实现更新 |
| S3 | 匹配安装包、签名更新、数据升级和八组合原生验收完成 | 汇总 S1/S2 的实现与证据，补真正缺失的发布条件 |

三份 spec 已整体获批；三份覆盖各自全部验收项的 plan 已写成，现一起送审。用户明确选择执行模式和依次执行的范围后，按该授权连续推进，不因每个小任务结束重复请求已授予的许可。旧自动确认授权仍无效；新发现的重要选型、权限扩大或 Hive 必需改造须集中说明，不能自动带入。

各 plan 完成要报告“用户现在能做什么”、未验证的真实环境与下一里程碑。只读账号观察已完成，不能再作为 S1 的新交付；S1/S2 核心功能也不能全部推给 S3。三份 spec 已获批准；对应 plan 和执行模式尚待用户确认，后续不得把文件存在或提交标题当作用户批准。
