# Bee 请求超时保活与重试设计

日期：2026-11-03。状态：用户已明确批准方案 A，进入实施。

## 1. 用户目标与既有约束

用户要求修复状态查询超时导致 Bee 退出的问题，增加重试机制；先描述现状，再确定优化方案。

继续遵守已批准的[连接与贡献分离设计](2026-11-03-desktop-device-connection-design.md)：App 已绑定就保持设备连接，是否贡献另行控制；在线与贡献交接可短暂重连，不修改 Hive。自动恢复不得开始贡献、选择账号或解除平台暂停。

本稿拟替代旧桌面桥中“任何已发送请求超时都终止管理会话”的规则；保留真实进程退出、管道损坏及协议完整性异常的处理。请求超时不证明 Bee 进程死亡，也不证明 Hive WebSocket 断开。

## 2. 当前实现与本次证据

通信链为：React 页面 → Tauri Rust 私有请求调度器 → stdin/stdout JSON 帧 → Go 管理子进程 → Hive HTTP。Hive WebSocket 由同一 Go 进程中的独立生命周期维持。

| 位置 | 已核对的行为 | 影响 |
| --- | --- | --- |
| `desktop/src/system/desktopState.ts` | 每个平台同时启动 `account_snapshot(refresh=true)` 和 `supply_status`；统一刷新通常在一轮结束后 10 秒再查 | 已有自动重查，不是完全没有重试 |
| `desktop/src-tauri/src/sidecar.rs` | 同平台读请求串行，跨平台可并行，共享操作保持屏障 | 不能随意放开同平台并发或越过写操作 |
| 同文件 `request_inner` | 多数请求自入队起只有 15 秒，包含排队、写管道和等待回复 | 排队消耗后续执行时间 |
| `agent/desktop_supply.go`、`agent/desktop_accounts.go` | 供给及账号快照通常在进入服务方法后设置 12 秒 context | Go 的执行期限与 Rust 剩余期限不同步 |
| Rust 调用方及 `session` 循环 | 两处都可将已发送请求超时升级为 `RESPONSE_TIMEOUT`，令桥进入 Failed | 只修改其中一处不能解决问题 |
| Rust `supervise` | 会话失败后关闭 stdin，回收本 App 拥有的 Bee；2 秒仍未退出则终止并等待 | 独立 WebSocket 和所有 worker 随进程一起消失 |
| 前端 native 状态处理 | 从 Ready 变 Failed 时清除旧快照、停止正常刷新入口 | 页面变成整页管理进程错误，无法自行恢复 |

截图请求为 `supply_status`，ID 为 `shell-2487`，未按时收到回复；回收后 `exit status: 0`。实际进程检查只剩 `bee-desktop` 桌面壳，Bee 子进程已不存在。`0` 是子进程退出结果，不是该查询成功。

本轮运行现有 Rust 测试 `sidecar::tests::sent_deadline_and_abandoned_caller_still_fail_closed`，退出码 0。该测试明确断言已发送请求超时或调用方离开后最终进入 Failed。日志：`.cache/bridge-retry-baseline.log`。这是现状复现证据，不是修复后的验证。

发现的时间预算冲突可用如下时序说明：同平台账号与供给查询都在 t=0 入队；账号查询到 t=10 才结束，供给查询在 t=10 发出，Rust 却在 t=15 判超时，Go 允许该供给查询执行到 t=22。即使供给查询自身只花 6 秒，也会触发整个进程回收。

这条时序由源码可直接推出，但本次 `shell-2487` 的实际排队及执行耗时未保存，不能声称已经证明现场由这一因素单独触发。休眠唤醒、慢 HTTP、锁等待等具体触发仍需新增阶段证据后区分。已确定的是超时被错误放大为进程失败的处理链。

仅延长统一超时或在 HTTP 内立即重试，不能消除“超时杀进程”，也不能处理迟到回复；不作为完整方案。超时后自动拉起另一个 Bee 会切断现有连接，并引入未决操作恢复和重复连接风险，不符合本次保活目标。

用户已确认方案 A，包括下述期限、重试节奏与致命异常边界。

## 4. 方案 A：请求失败与进程生命周期分离

### 4.1 明确请求阶段

区分未发送、写入中、已完整发送待回复、调用方已超时但原请求尚未结束、已结束。

- 未发送时超时或取消：移除队列项，证明没有发出字节，返回原有明确未提交语义。
- 已开始发送后超时：结束调用方本次等待，记录结果未知，但不把管理桥改为 Failed，不关闭 stdin，不取消 Bee 运行上下文。
- 部分帧已写入：保留原帧剩余字节，继续同一次写入，不重发前缀，不插入下一帧；不能把部分帧当作已完整发送。
- 完整帧已发送：继续收取和校验该 ID 的最终回复。超时本身不是取消完成的证明。
- 调用方离开页面或取消等待，遵守相同规则，不能撤销已发出的业务动作。

两处超时判定共用上述生命周期规则，消除调用方计时器和监督循环互相覆盖状态的竞争。

### 4.2 原请求、迟到回复和资源上限

保留原请求 ID、原实例及所占通道／共享屏障，直到真实回复结束。迟到回复仍校验协议版本、实例、ID 和响应格式；消费后释放资源，但不回填已经失效的 UI 请求，不覆盖较新的绑定、网络或操作修订。需要展示当前结果时重新读取快照。

原生壳在已超时请求真正结束后发出仅用于刷新调度的完成事件，携带实例、请求 ID、方法和平台，不携带结果正文。统一刷新器据此解除对应等待，开始退避计时并安排一次新核对；旧实例事件忽略，绑定／网络已变化时只核对当前上下文。事件不改变贡献状态、不重放写入。这样无需用户点击，也无需在旧请求尚未结束时持续往队列中追加探测。事件丢失时，已有低频协调核对可以查询原生壳内存中的在途状态后恢复调度；该查询不进入 Go 业务队列。

在途请求仍计入现有最多 16 项的总预算；同一平台的旧请求未结束前，不重复发送该平台请求，也不放行其后的共享写操作。其他原本允许并发的平台读取继续按既有规则进行。重复刷新合并或返回明确“前次请求仍在结束中”的局部状态，不能无限积累后台请求和已超时 ID。

如果某个操作一直不返回，保留进程、保留原操作状态，阻止冲突操作并报告等待结束；不声称一定会在 N 秒内恢复、不通过丢弃记录假装取消成功。正常网络请求仍受 Go context 约束，应能退出本轮；真正无法结束的本地阻塞记录为独立故障。用户明确退出仍可走现有受控回收。

### 4.3 分开排队期限与执行期限

- 普通请求：排队最多 15 秒；首次实际写出字节后开始本次执行期限，通常 15 秒，包括剩余帧写入和回复。
- Go 常规账号／供给方法保留现有 12 秒执行预算；检查其内部网络调用、可取消的等待是否都使用同一个 context，不在后续子步骤重新扩大预算。
- 官方账号核验等特殊长请求保留专用执行上限，不能统一缩成 15 秒。
- 握手及明确退出／更新保留既有整体期限，不因普通请求预算拆分而延长退出等待。
- 统一刷新器同平台先查账号、再查供给，跨平台仍可并行；每次请求真正准备发起时才创建它的等待预算。
- 休眠唤醒后只恢复一轮必要核对，合并积压刷新；超时不代表需要结束 Bee。

普通请求最坏等待由原来的合计 15 秒变为最多排队 15 秒加执行 15 秒。界面必须分清排队、读取和原请求未结束，不能始终显示无解释的加载。

## 5. 重试归属与错误分类

只保留一个 UI 自动核对调度者 `createDesktopState`。Rust 桥不自动重放请求，Go HTTP 不为此次功能叠加嵌套重试。WebSocket 继续由 Go 独立使用现有 1 秒起、上限 30 秒的退避，避免状态查询与 WebSocket 重连相互驱动。

建议状态读取连续失败后的基准等待间隔为 **2、4、8、16、30 秒**；达到上限后持续核对，不以失败次数耗尽为由退出 Bee。实际间隔在 `[0.8d, d]` 内加入小幅随机抖动，最大不超过 30 秒；测试使用可控随机源。成功后清零连续失败次数并回到正常 10 秒刷新。某一平台失败不让另一平台退避升级。

已收到失败回执时，从该回执开始等待；原请求回复超时但仍在途时，先等原请求真正结束，再开始等待。原请求尚未退出时不能发起下一次尝试，也不能显示一个无法兑现的重试倒计时。普通轮询不能绕过尚未到期的重试时刻，操作进行中的 400 ms 快速核对也不能挤压失败资源的退避。已有官方额度刷新有效期、最早允许查询时间与限流上限继续生效。

| 失败 | 动作 | Bee 进程 |
| --- | --- | --- |
| 本地队列超时、完整请求回复超时 | 记录本次状态；原请求结束后再核对 | 保留 |
| HTTP 超时、明确的连接中断／临时 DNS 故障、502/503/504 | 只读核对按退避继续 | 保留 |
| HTTP 429 | 服从可验证的服务端 Retry-After；本地退避不得早于服务端要求 | 保留 |
| 401/403、设备被替换、来源缺失、凭证非法、TLS 证书校验失败 | 停止相关业务的自动重试，显示对应处理入口；已批准的身份保护及连接占用规则不变 | 保留 |
| 首次连接 409／归属未确认 | 保留现有停止抢占规则 | 保留 |
| 输入非法、状态修订冲突、持久数据损坏 | 阻断相关操作，不作为临时网络错误重试 | 保留；保留启动核验失败等既有保护 |
| 真实子进程退出、管道不可恢复地断开、错误实例／版本／未知或重复 ID／非法帧 | 私有会话不可继续信任，维持现有终止会话及 owned 回收 | 不承诺维持；不自动开启新实例 |
| 用户明确退出、安装更新 | 冻结新动作，回收 owned worker 与进程 | 正常退出 |

分类依据为错误类型、稳定错误码和 HTTP 状态，不能靠匹配错误文本决定重试。总括性的“结果未确认”不等于网络可重试。未知类型保留未知状态并阻止自动重放，不擅自归入连接中断。

## 6. 写操作与业务读取的边界

暂停／恢复接单、开始／停止贡献、账号接入／换号、配对和官方登录均不由通用重试器重新提交。超时后保持原操作记录、账号候选及绑定上下文，通过已有运行快照、原操作 ID 或 GET 读回核对。确认成功前，依赖该结果的新动作保持阻塞。

不能仅按方法名含 `status`／`snapshot` 就判为纯读取：

- `device_status` 在配对过程中可能推进已授权的兑换或保存。
- `account_snapshot(refresh=true)` 可能启动既有未决账号动作的核对 worker。

这些入口只沿原有持久记录和已授权恢复流程继续，不放入通用“重新提交相同命令”的透明重试。原操作尚在途时先等待；后续正常核对必须使用当前有效绑定、网络及原操作记录，不新建操作 ID，也不恢复未经授权的写步骤。

停止贡献与退出的含义继续分开：用户停止贡献仍恢复设备在线；真正退出关闭全部连接。此次局部查询失败既不写停止意图，也不新增开始贡献意图。

## 7. 界面与诊断

沿用当前界面样式和局部失败展示，不重做布局，不增加全局“全部重试”。失败出现在对应平台或状态区域，保留导航和其他有效数据；过期数据明确标为待核对，不能继续宣称当前已连接或可接单。

建议显示实际含义：

- 供给读取失败：平台接单状态暂未核对，显示本次具体失败原因及已安排的重试。
- 原请求未结束：前次核对尚未结束，结束后重试；不伪造下一次重试时间。
- 写操作回执超时：操作结果待确认，正在核对原操作；不显示可立即重复提交的同名按钮。
- WebSocket 状态继续取真实运行快照；供给 HTTP 查询失败不把连接改成断开。若运行快照也已过期，显示连接待确认。
- 恢复后使用新快照撤销当前错误，保留历史诊断，失败时不反复弹系统通知。

沿用 `ui-ux-pro-max` 的局部错误、明确恢复路径和无障碍反馈，以及 `interaction-design` 的保留上下文原则；文案沿用当前产品术语。等待、重试和阻塞由调度事实驱动，不用文案推断网络状态。

新增白名单诊断证据：请求 ID、方法、平台、阶段、排队耗时、执行耗时、请求是否完整发送、是否仍在途、连续失败次数及实际下次尝试时刻。Go 记录身份核对／供给 GET 等阶段的开始与结束、耗时及安全错误类别。错误输出与本地日志均保留这些证据；不记录 token、auth.json、请求正文或任意 stderr 原文。

新错误字段须同步 Go/Rust/TypeScript 的严格校验及日志白名单，不能通过宽松反序列化绕过契约。

## 8. 验收

1. 同平台账号查询 10 秒、供给查询 6 秒的可控场景成功；排队不吞掉供给执行预算，Bee PID/instance 不变。
2. 单次和连续多次供给超时，Bee 存活；已有 WebSocket 不因查询失败关闭；另一平台按既有并发规则可读。
3. 请求超时后迟到成功／失败回复被按原 ID 消费，不触发 unknown ID，不覆盖新快照；重复、伪造和跨实例回复仍拒绝。
4. 部分帧写入、调用方取消、满队列和长期不返回场景不重复发送、不无限增长、不绕过共享写屏障。
5. 断网、超时及 503 后按已显示的退避核对，恢复后自动显示新状态；429 不提前重试；401/403、TLS 校验错误和非法数据不无限重试。
6. 暂停／恢复、启停、接入／换号的丢失回执场景，真实写请求计数最多一次；已有操作核对正确恢复。
7. 休眠／恢复或等价的计时器延迟测试，不因过期定时器回收健康 Bee，不突发补发所有轮询。
8. 退出与更新仍可在既有期限内回收拥有的资源；失败不伪报已退出，外部 Bee 不受影响。
9. Go/Rust/TypeScript、严格桥契约、前端恢复路径通过；重建原生 App 验证已绑定、贡献未启动时的连接与局部失败恢复。故障注入使用本地服务和合成账号，不操作用户真实平台写入。

## 9. 实施边界与本轮检查

预计涉及 Rust 私有桥／测试、Go 请求边界及诊断、统一刷新器与局部错误展示、三端契约及相应用例。不开新守护进程，不做崩溃自动重启，不改变已批准的贡献权限和 Hive 协议；保留工作区现有改动，不提交、不发布。

用户于 2026-11-03 明确要求“按照方案 A 修复”；按本设计创建实施 Plan 并继续实现，无需重复确认。

文档自检：现状复现与未来验收分开；现场触发原因的不确定性已标注；方案 A 说明长期不返回时的限制；重试只由一个调度器拥有；写操作、迟到回复、部分帧和真实进程故障均有边界。
